# LifeQuest H5 响应式重设计方案

## 背景

当前 `frontend/` 已有一套可同时运行在 Web 和客户端容器中的 Vue 3 界面，但 H5 页面主要是在桌面布局基础上通过响应式收缩得到：

- 桌面端以固定侧边栏 + 顶部栏为主结构。
- 手机端额外叠加底部导航，但很多页面主体仍保留桌面信息组织方式。
- 首页、待办、商城、个人中心等页面存在较大的卡片、偏宽的横向操作区、重复页头和偏展示型的留白。
- 在移动端宽度下，内容占位过大，首屏有效信息偏少，主要操作区不够集中，页面不够适合单手使用。

本次工作不新建独立 H5 项目，不改路由和核心功能，不重做产品信息架构，而是在当前项目内完成一轮移动端优先的响应式样式重设计，并保持桌面端与客户端可继续使用。

## 目标

- 在现有项目内完成一套统一的移动端优先响应式样式体系。
- 保留现有路由、数据流、接口调用和主要交互能力。
- 允许中度重排页面信息顺序、头部结构、卡片层级和操作区位置。
- 让手机端页面在 `375px` 宽度下更紧凑、更易读、更易点按。
- 同时兼容客户端和桌面端，不做“只适配手机、破坏桌面”的单端改造。
- 建立可复用的全局布局规则，避免后续页面继续各自补丁式修样式。

## 非目标

- 不新建独立移动端前端项目。
- 不修改后端 API、数据库和业务规则。
- 不在本次中引入新的 UI 框架或大规模替换 Element Plus。
- 不重构所有页面的业务组件边界；仅在当前改造范围内做必要的结构整理。
- 不追求完全不同的品牌视觉方向；保留 LifeQuest 当前清爽、轻游戏化的气质。

## 已确认范围

本次按以下顺序推进页面设计与实现：

1. 首页
2. 待办
3. 商城
4. 个人中心

其余页面本次不做完整重设计，但新建的全局布局规则必须为后续页面复用留出空间。

## 推荐方案

采用“统一移动端设计层 + 页面顺序重排”的方案，而不是逐页做局部补丁。

理由：

- 现有问题不只存在于某个页面，而是贯穿布局容器、头部、卡片密度、操作区和导航结构。
- 如果只做页面级补丁，会继续保留“桌面布局缩小到手机上”的基础问题，后续维护成本会越来越高。
- 统一全局样式变量、间距、断点和页面容器后，再逐页重排首页、待办、商城、个人中心，能让设计收敛到同一套规则下。

## 设计原则

### 1. Mobile-first

以手机端作为主设计基准，先定义窄屏下的内容层级、触达区和视觉密度，再向平板与桌面扩展。

### 2. 操作优先

移动端页面优先保证用户最常用操作和最重要信息进入首屏，装饰性内容和次要信息后置。

### 3. 紧凑但不拥挤

减少无效留白、装饰大图标和厚卡片，但不牺牲可读性与点按体验。通过重排信息层级而不是简单缩小所有元素来获得空间。

### 4. 单列优先

移动端默认采用稳定的单列内容流。桌面端再恢复更宽松的多列结构，不允许多列内容直接硬挤到手机宽度中。

### 5. 全局统一

头部高度、页面内边距、卡片半径、按钮尺寸、列表节奏、底部安全区等规则统一收敛，避免每页有自己的一套移动端写法。

## 全局响应式设计

### 断点策略

- `0 - 767px`：手机端主布局
- `768 - 1199px`：平板 / 窄客户端
- `>= 1200px`：桌面端

实现上采用移动端默认样式，向上使用 `min-width` 或现有结构中等价的上行断点增强。

### AppLayout

保留现有 `AppLayout + Header + Sidebar + bottom-nav` 基本结构，但调整职责：

- 桌面端继续使用侧边栏布局。
- 手机端主内容区改为真正的单列内容流，不再以桌面内容区缩窄作为基础。
- 页面内容区统一承担底部导航和安全区留白，避免各页面重复处理底部空间。
- 页面主容器需要统一最大宽度、左右内边距和垂直节奏。

### Header

手机端头部需要明显压缩：

- 降低头部高度和左右 padding。
- 弱化头像/用户名组合的占位。
- 减少视觉噪音，突出页面标题和必要操作。
- 页内重复大标题区需要合并或收缩，避免“Header 已有标题，页面内部再来一块大页头”。

### Bottom Navigation

底部导航保留，但需要重新约束：

- 保证触达区不小于 `44x44px`。
- 控制导航高度，避免过厚。
- 图标与文字比例更紧凑，激活态清晰。
- 页面底部统一预留导航高度和安全区，不允许局部页面遮挡内容。

### 内容容器与间距

全局统一移动端布局节奏：

- 手机端页面横向 padding 需要比当前更克制，但保持稳定一致。
- 模块之间的垂直间距缩短。
- 卡片内部 padding 下降，减少大面积空白。
- 列表项优先使用“薄卡片”或“列表项”而不是厚重展示卡。

### 控件与触达区

- 所有核心交互元素保持至少 `44x44px` 命中区。
- 相邻可点击元素之间至少保留 `8px` 间隔。
- 按钮、图标按钮、标签切换、底部导航均遵循相同触达标准。
- 通过 padding 扩大点击区域，而不是一味放大视觉图标尺寸。

### 视觉语言

保留现有浅色、清爽、轻游戏化方向，但整体更偏工具型应用：

- 弱化过大的装饰图标和展示型首屏。
- 缩减阴影和不必要的层层包裹。
- 用清晰的信息优先级替代夸张的视觉占位。
- 保留当前主要颜色体系，必要时微调变量以增强轻量感和层级对比。

## 页面设计

### 首页

当前首页问题：

- 签到卡与欢迎卡分离，首屏高度被吃掉太多。
- 统计卡体积偏大。
- 最近任务、最近目标和今日任务都使用相对厚重的内容块，移动端信息密度偏低。

改造方案：

- 将欢迎信息、签到状态、基础角色摘要整合为紧凑首屏卡，减少重复模块。
- 统计区从大卡片改为更薄、更强调数字的摘要卡，重点展示等级、金币、待办数。
- `今日任务` 前置为首页主内容，让用户进入首页后能优先看到当日可执行项。
- `最近任务` 与 `最近目标` 改为上下排列的轻量模块，每个模块只保留最必要信息。
- 任务/习惯/目标项改为扁平列表式结构，减少厚卡片、长描述和多余装饰。
- 桌面端保留较宽松分区，但与手机端共用同一套组件密度与结构原则。

### 待办

当前待办页问题：

- 页头、新建按钮、tab 区块都偏高。
- 习惯/任务/目标的 tab 更像桌面卡片，不够适合手机端。
- 卡片默认承载过多信息和横向操作，窄屏下容易显得拥挤。
- 编辑、删除、完成等操作在卡片内竞争视觉焦点。

改造方案：

- 页头压缩成更短的操作头，只保留标题、计数和主要新建操作。
- tab 改成更紧凑的移动端切换条，减少高度占用。
- 列表卡片统一瘦身：第一层显示标题和核心状态，第二层显示奖励、频率、项目等次要信息。
- 默认把次要信息后置或折叠，不让所有字段同时占据首屏高度。
- 完成、编辑、删除操作重新归位，优先保证主操作明确，次级操作不抢主视觉层级。
- 任务的项目标签、状态、奖励等信息在手机端采用换行或次行策略，而不是强行横向塞入一行。

### 商城

当前商城页问题：

- 顶部余额、历史、新建商品操作横向排布偏桌面化。
- 商品卡片偏厚，图标区与操作区占位不够经济。
- 作者操作和购买操作在同一层竞争注意力。

改造方案：

- 页头区重排为更符合手机端的层级：优先显示余额和主要操作，次要入口降级。
- 商品列表改为更紧凑的移动端商品卡或列表卡，突出商品名、价格、库存和购买行为。
- 编辑/删除等管理操作下沉到次级层级，避免与购买操作争夺首要位置。
- 库存、分类、价格信息使用更紧凑的标签与信息列，不再拉大纵向高度。

### 个人中心

当前个人中心问题：

- 资料头、统计卡、成就区和称号区可能存在“大块但信息少”的展示倾向。
- 用户最常操作的信息不一定在最前。
- 弹窗和卡片密度偏桌面，手机端显得厚重。

改造方案：

- 用户资料头压缩为紧凑摘要，突出头像、昵称、称号、等级等关键信息。
- 将常用操作和关键信息前置，展示型内容和收藏型内容后置。
- 统计区、成就区、称号区统一采用更轻量的卡片密度和更明确的分组。
- 称号弹窗等覆盖层在手机端优化尺寸、边距和滚动体验。

## 实现边界

### 允许调整

- 页面信息顺序
- 页面局部结构层级
- 头部和页头关系
- 卡片和列表的布局方式
- 按钮和操作区位置
- 全局 CSS 变量、布局变量和断点

### 不允许调整

- 页面路由语义
- 核心业务功能
- 接口调用时机和业务规则
- 用户已习惯的主要导航入口名称

## 技术实施建议

### 推荐落点

优先在以下区域建立统一规则：

- `src/App.vue`：全局设计变量、基础样式和断点变量
- `src/components/layout/AppLayout.vue`：内容区、底部导航、移动端主布局
- `src/components/layout/Header.vue`：统一头部尺寸和移动端结构
- 各页面自身样式：按页面顺序重做手机端布局

### 样式策略

- 先建立全局变量和容器规则，再进入单页改造。
- 页面内尽量复用统一的卡片、列表、模块节奏，而不是每页定义完全不同的视觉规则。
- 对现有页面尽量做结构保守的模板调整，避免改动业务逻辑。
- 如页面内样式块过大且混乱，允许顺手清理明显重复的样式职责，但不做与本次目标无关的重构。

## 验收标准

### 视觉与布局

- `375px` 宽度下首页、待办、商城、个人中心首屏有效信息明显提升。
- 手机端不出现横向滚动。
- 卡片、列表、页头和底部导航视觉密度统一。
- 页面主要操作位置明确，不出现多个同优先级按钮横向挤压。

### 响应式兼容

- 手机端、平板/窄客户端、桌面端都能正常显示。
- 手机端改造不破坏桌面侧边栏和主布局可用性。
- 内容不会被固定头部或底部导航遮挡。

### 交互

- 主要可点击元素触达区满足移动端操作要求。
- 焦点状态、hover/active 态保持可识别。
- 弹窗、下拉、底部区域在移动端可正常操作和滚动。

### 验证方式

- 运行 `cd frontend && npm run build`，确保构建通过。
- 至少在 `375px`、`768px`、`1024px`、`1440px` 四档宽度检查页面表现。
- 手工检查首页、待办、商城、个人中心的头部、列表、卡片、弹窗和底部导航。

## 实施顺序

1. 建立全局移动端设计变量与布局规则。
2. 调整 `AppLayout`、`Header`、底部导航和内容容器。
3. 重做首页移动端布局。
4. 重做待办移动端布局。
5. 重做商城移动端布局。
6. 重做个人中心移动端布局。
7. 进行多断点回归验证并修正桌面端兼容问题。

## 风险与注意事项

- 现有页面样式较分散，单页改造时可能暴露更多全局布局重复问题，需要优先在布局层收口。
- Header、页面内部页头和底部导航之间若职责不清，会导致局部页面重复留白，需要在早期统一。
- 个别页面可能存在桌面端默认的横向信息布局；移动端适配时应优先重排，而不是简单缩小字号。
- 如果改造中发现某页面模板结构与样式严重耦合，可以做局部结构整理，但必须保持功能行为不变。
