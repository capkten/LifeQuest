# LifeQuest Full Closure Design

**Date:** 2026-08-22  
**Status:** Approved design  
**Scope:** Complete product-level closure of the current LifeQuest v1.0.0 project

## Goal

把 LifeQuest 从“核心功能可运行、部分修仙功能已实现”推进到完整可发布状态：通用稳定性、凡界修仙资源闭环、宗门/世界/NPC 状态机、飞升后的完整仙界成长循环，以及最终质量门禁全部具备实现和验证证据。

## Product decisions

### 1. 飞升不是赛季，也不是重置

飞升是用户达到渡劫条件并成功完成渡劫后的单向状态转换：

```text
凡界档案
  ├─ 未满足条件：继续凡界成长
  └─ 满足条件并成功飞升：
       ├─ 保留凡界历史档案
       ├─ 激活仙界档案
       └─ 开始仙界成长循环
```

不创建赛季，不重置用户，不删除凡界任务、功法、宗门、NPC 或历史奖励。

### 2. 双轨数据模型

现有凡界数据继续作为主历史档案；新增独立的仙界档案，只在用户首次成功飞升时创建。仙界档案不得覆盖凡界境界、修为或历史记录。

飞升操作必须幂等：重复请求只能返回同一飞升结果，不得重复创建档案、发放奖励或扣除资源。

### 3. 飞升后仍可完成凡界待办

飞升后用户仍可查看、创建和完成凡界待办。每次待办只产生一份结算结果：

- 凡界修为奖励不再增加凡界修为；按固定规则转换为仙元。
- 凡界灵石奖励按固定规则转换为仙石。
- 没有明确映射关系的凡界奖励不自动生成仙界奖励。
- 原始奖励、转换奖励、来源键和结算状态必须写入同一条可审计记录。

修为不做跨界数值继承；飞升后从独立仙元体系开始。跨界比例为代码中的固定常量，不做后台配置中心。

### 4. 仙界是完整产品级循环

仙界不是占位页面。首版必须支持持续游玩：仙界境界、仙元、仙石、地图区域、仙官委托、仙界活动、奖励、晋升条件和阶段目标形成闭环。仙界活动至少有一种可重复执行的活动和一种有冷却或阶段限制的活动。

## Architecture

系统分为四个领域边界：

1. **Mortal domain**：现有待办、凡界境界、修为、灵石、功法、宗门、NPC 和渡劫。
2. **Transition domain**：渡劫成功、飞升事务、双轨档案创建、跨界奖励转换和幂等审计。
3. **Immortal domain**：仙界档案、仙元、仙石、仙界境界、地图、仙官、任务、活动和晋升。
4. **Presentation/verification layer**：Vue 页面、统一错误映射、请求代际保护、操作锁、Playwright strict 合同和 completion ledger。

领域服务负责规则和事务；API 层只负责认证、输入校验、调用服务和稳定错误码；前端不得自行推导权威资源、条件或奖励结果。

## Data model

新增模型必须与现有 SQLAlchemy 模型和迁移模式一致，具体表名在实现计划中固定。最少包含：

- `ImmortalProfile`：`user_id` 唯一、飞升时间、当前仙界境界、仙元、仙石、状态。
- `ImmortalRegion` / `ImmortalProgress`：区域、解锁状态、阶段进度和解锁来源。
- `ImmortalOfficial`：仙官身份、关系值、声望、可用委托。
- `ImmortalActivity` / `ImmortalActivityLog`：活动类型、冷却、状态、奖励来源键。
- `AscensionRecord`：用户、凡界快照、飞升结果、幂等键、时间和转换汇总。
- `CrossRealmSettlement`：原始奖励、转换奖励、来源键、结算状态和唯一约束。

凡界资源增长路径需要补齐：渡劫丹库存、功德、资质、心境、宗门贡献和功法效果。所有涉及奖励的来源键必须可唯一识别，并在数据库层防止重复结算。

## Mortal cultivation rules

### Tribulation

渡劫服务必须按固定顺序检查：

1. 当前境界和目标小境界。
2. 冷却时间。
3. 渡劫丹库存和本次消耗数量。
4. 目标完成度。
5. 习惯连续完成条件。
6. 重要历练条件。
7. 宗门贡献或脱离宗门条件。
8. 准备度和成功率。

检查失败时返回机器可读错误码和用户可读参数；成功时同一事务内扣除资源、写入结果、更新境界或飞升状态并结算奖励。

### Cultivation resources

功德、资质、心境、宗门贡献和渡劫丹必须至少各有一个真实来源和一个真实消耗或作用点。不能只在页面展示静态字段。

### Techniques

功法学习、装备、卸下和冲突规则继续由服务端权威校验。装备效果必须参与修炼效率、待办奖励或渡劫准备度计算，并有结构化效果测试和并发槽位测试。

## Sect, world and NPC rules

- 宗门试炼必须包含目标、条件、进行中、成功、失败和奖励状态。
- 宗门偏好、核心传承和贡献必须影响至少一个任务、功法或成长结果。
- 隐藏宗门必须有可测试的现身条件和解锁路径。
- 地图节点按区域和前置条件渐进开放，不得在达到单一境界后一次性开放全部节点。
- NPC 关系必须有唯一性约束、人口上限、重复事件冷却和状态转移校验。
- 所有非法状态转移返回稳定错误码，前端显示可操作的原因和下一步。

## Frontend behavior contract

所有新旧页面统一遵守：

- 请求中显示明确 loading，且只由最新请求清除。
- 业务锁定按钮保持可点击，点击后显示原因；只有网络请求处理中使用原生 `disabled`。
- 请求失败不伪装成成功空状态；保留已有数据并显示重试入口。
- 写操作使用独立 action lock，失败后保留表单和上下文。
- 后端错误码通过共享转换器映射为中文文案。
- 关键写操作必须有浏览器合同测试，覆盖成功、失败、重复点击、快速切换和重试。

## Verification strategy

每个子项目必须先写失败测试，再实现，再运行独立验证：

- 后端：目标测试、全量 `pytest -q`、并发/幂等/迁移测试。
- 前端：相关 Node 回归测试、全量前端回归、`npm run build`。
- 浏览器：375x812、768x1024、1024x900、1440x1000 四种视口；记录 URL、DOM 断言、请求失败、控制台错误和截图。
- 数据：旧用户无损进入凡界；首次飞升创建仙界档案；重复飞升和重复奖励不产生副作用；迁移失败可回滚。
- 质量：completion ledger 状态必须与证据一致；任何只有静态证据的项目不得标记为 `verified`。

## Delivery decomposition

### Workstream 1: General stability closure

完成 G-11、G-12、G-13，并补齐真实浏览器验收。

### Workstream 2: Mortal cultivation closure

完成渡劫丹、前置条件、资源增长、功法效果、准备度和统一错误码。

### Workstream 3: Sect/world/NPC state machines

完成宗门试炼、贡献/传承/偏好、隐藏宗门、地图推进和 NPC 约束。

### Workstream 4: Ascension and immortal loop

完成飞升事务、仙界档案、仙界资源、地图、仙官、活动、奖励、晋升和凡界待办跨界结算。

### Workstream 5: Release quality gate

同步台账、运行全量测试、浏览器合同、迁移回滚、部署冒烟、bundle 优化和最终发布报告。

## Dependencies and parallelism

- Workstream 1 可独立执行。
- Workstream 2 可与 Workstream 1 并行。
- Workstream 3 依赖 Workstream 2 的资源、贡献和功法接口。
- Workstream 4 依赖 Workstream 2 的渡劫/奖励接口，以及 Workstream 3 的宗门/世界状态。
- Workstream 5 在前四项稳定后执行。

允许其他模型并行处理 Workstream 1 和 Workstream 2；Workstream 3、4 必须基于已批准的接口契约，不得各自发明资源或飞升规则。

## Completion criteria

项目只有在以下条件全部满足时才可宣称完成：

1. 所有 planned ledger items 已变为 implemented 或 verified。
2. 关键项均有动态浏览器证据。
3. 后端和前端全量测试通过。
4. 迁移、回滚、幂等和并发测试通过。
5. 飞升前后待办奖励无重复结算，修为不错误跨界继承。
6. 仙界活动可持续执行并产生可审计奖励。
7. 发布报告、部署冒烟和已知警告均有明确记录。
