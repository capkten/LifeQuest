# LifeQuest 稳定性、今日工作台与习惯闭环设计

**日期：** 2026-09-12  
**当前版本：** `1.13.0`  
**状态：** 已获准进入设计文档阶段，尚未进入代码实现

## 1. 目标

本轮修复两类问题：

1. 关闭上一轮审查中已经复现的项目权限、财务余额、习惯统计、补记上限、奖励判定和前端日期问题。
2. 对已标记完成的 FEAT-01 今日工作台和 FEAT-02 习惯计划与记录能力重新按业务不变量验收，补足可能被现有测试遗漏的边界场景。

本轮的完成标准不是“现有测试继续通过”，而是每一条跨页面、跨接口和跨中国日期边界的规则只有一个权威实现，并且有可重复的失败前回归测试和成功后验收证据。

## 2. 范围

### 2.1 包含

- 项目任务读取、项目统计和旧非法关联的用户隔离。
- 财务流水新增、修改、删除和转账修改的余额原子性及失败回滚。
- 同一中国日的首笔财务流水经验奖励判定。
- 每周目标习惯的计划槽位、完成率、历史统计、连续周期和补记上限。
- 暂停、请假、补记、备注和完成记录在列表、首页、日历、历史接口中的一致性。
- 前端财务、债务、日历、首页和习惯页面的中国日期工具统一。
- FEAT-01 工作台的任务分组、今日重点、快速创建、完成结算、并发冲突、失败重试和移动端验收。
- FEAT-02 页面交互、错误状态、重复操作抑制、跨入口一致性和移动端验收。
- 与上述规则直接相关的后端、前端和浏览器回归测试。

### 2.2 不包含

- FEAT-03 至 FEAT-10 的新功能开发。
- ENG-02 的完整测试自动发现改造。
- ENG-03 的大包拆分和编辑器依赖优化。
- ENG-05 的大型服务拆分；本轮只允许增加必要的小型规则辅助模块。
- ENG-06 的仓库说明全面重写。
- 退款政策变更。当前继续采用“不支持部分退款、按同种可用背包数量整体核验、不绑定具体背包物品来源”的已确认规则。
- 根据 `last_completed_at`、连续数或其他间接字段推测并补造无法证明的历史完成记录。

## 3. 已确认的根因

| 编号 | 现象 | 根因 | 影响 |
| --- | --- | --- | --- |
| SEC-01 | 项目任务接口和统计可能包含其他用户任务 | `ProjectService` 的任务查询只按 `project_id`，没有在读取边界再次按 `Task.user_id` 过滤 | 私有任务泄露，项目进度被污染 |
| FIN-01 | 修改转账金额可把来源账户改成负数 | 更新流水先反向旧流水，再用不带 `require_sufficient` 的普通余额变更应用新流水 | 资产约束只覆盖新增接口，不覆盖修改接口 |
| FIN-02 | 同日第二笔流水也可能领取首笔经验奖励 | 新流水在 `_award_transaction_exp` 查询之后才 flush；测试会话明确使用 `autoflush=False` | 奖励重复，结果依赖 flush 时机 |
| HAB-01 | 每周目标的列表完成率和历史完成率不同 | `_habit_metrics` 按周目标计算槽位，`get_habit_history` 按每日 `scheduled` 计数 | 用户在不同页面看到互相矛盾的完成率 |
| HAB-02 | 补记可以绕过每周 N 次上限 | 普通打卡检查 `_weekly_completion_count`，`backfill_habit` 没有同样检查 | 真实完成记录超过目标，连续周期和奖励规则失真 |
| DATE-01 | 财务页面使用 UTC，日历使用浏览器本地日期 | 页面各自使用 `toISOString()` 或 `new Date()`，没有统一中国日期工具 | 中国午夜附近默认日期、今天标记和显示口径不一致 |
| WB-01 | 工作台已具备幂等和冲突保护，但需要重新验证边界 | 工作台同时依赖后端日期分组、持久化重点、幂等请求和前端异步状态机 | 任一层异常都可能造成假完成、重复创建或覆盖他人选择 |

## 4. 业务不变量

### 4.1 所有权和读取隔离

- `Task.user_id` 必须等于访问者用户，才能从任何项目任务列表、项目详情、项目统计、待办列表、日历或工作台返回。
- `Project.user_id` 必须等于访问者用户，才能作为任务的项目关联或被读取。
- 对已有数据库中的非法旧关联采用“读取隔离”而非推测性修复：隐藏非法任务及其项目名称和统计贡献；不自动修改历史任务归属。
- 所有写入入口继续校验项目、阶段、里程碑的用户归属和层级关系。

### 4.2 财务余额和流水原子性

- 每一个会减少账户余额的有效操作都必须通过带余额条件的原子更新。
- 修改流水的顺序固定为：锁定用户和当前流水、反向旧影响、校验并应用新影响、提交；任一环节失败则整个事务回滚，旧流水和旧余额保持不变。
- 反向旧影响不因为当前账户余额不足而失败；应用新的支出或转账扣款必须检查余额。
- 转账修改必须同时校验来源账户、目标账户、来源与目标不同、金额为正以及账户归属。
- 新增、修改、删除和转账使用 `Decimal` 计算；余额变更不允许由 Python 读取旧值后覆盖写回。
- 首笔流水奖励的查询必须看到当前待保存流水，并在同一用户锁内完成；同一中国日最多一笔首笔奖励。流水失败回滚时奖励也回滚。

### 4.3 习惯计划和完成记录

习惯规则以中国本地日期为输入，以 `habit_completions(habit_id, completed_on)` 为事实来源。

- 每个习惯同一中国日最多一条完成记录。
- 每周目标习惯的周期为周一至周日；每个包含至少一个有效计划日的周期贡献 `weekly_target` 个计划槽位。
- 每周目标习惯的完成槽位为每周期 `min(实际完成数, weekly_target)`；完成率分子和分母在待办列表、首页、历史接口和统计中使用同一计算函数。
- 历史查询区间内，只要某周与区间相交且该周有有效计划日，就纳入该周的目标槽位；可见日期仍逐日展示，`scheduled` 表示该日可执行，不表示每天新增一个目标次数。
- 普通打卡和补记都必须检查该中国周剩余目标次数。达到目标后返回 `409`，不新增完成记录、不发放奖励、不改变连续周期。
- 补记只能写入最近 90 天内、习惯创建日之后、该习惯有效计划日且不在暂停/请假区间的日期；补记不发放奖励，并在历史记录中标记 `is_makeup`。
- 暂停和请假日期从计划分母和连续周期中排除；恢复日期采用半开区间语义重新纳入计划。
- 累计完成次数、当前连续周期、最佳连续周期和完成率是四个独立指标，不用 `last_completed_at` 替代完成历史。

### 4.4 中国日期

- 后端继续以 UTC 保存时间戳，以 `Asia/Shanghai` 计算业务日期和日期区间。
- 前端所有“今天”“昨天”“日期输入默认值”“日历当前月/今天标记”都通过一个共享工具计算，不直接调用 `toISOString().slice(0, 10)` 或浏览器本地 `getFullYear/getMonth/getDate` 作为业务日期。
- 前端接收带时区时间戳时，按中国时区转换；接收纯日期字符串时，按日期键展示，不把它再次解释为浏览器本地时间。

### 4.5 今日工作台

- 工作台日期由服务端返回，是当前中国日期；客户端不能用本地日期覆盖服务端日期。
- 任务分组只包含 `pending` 和 `in_progress` 任务：无截止日期为“未安排”，中国日期等于工作台日期为“今日到期”，小于为“逾期”，大于为“稍后到期”。
- 今日重点最多三项，保留用户选择顺序；已完成重点当天仍可展示，已取消或无权访问的任务不可展示或保存。
- 今日重点保存使用用户级锁和 `revision` 乐观并发控制；旧 revision 返回 `409`，不得静默覆盖另一设备的选择。
- 快速创建的 `request_id` 与请求内容绑定；同一用户、同一请求 ID 和同一内容只创建一条任务，内容不同或原任务已删除时返回明确冲突。
- 完成任务必须使用与待办和项目入口相同的服务端结算路径。前端只有收到服务端成功响应后才能显示成功；奖励刷新失败只能显示“操作已保存、请刷新”，不能要求用户重复提交。
- 加载失败不能渲染成合法的空工作台；已有数据刷新失败时保留旧数据并提供重试入口。
- 旧请求返回、离开页面、重复点击和网络超时不能覆盖较新的状态或触发重复奖励/回调。

## 5. 设计方案

### 5.1 后端规则边界

继续使用现有服务层和事务装饰器，不做大规模重构：

- `ProjectService`：给项目详情、项目任务列表和项目统计增加统一的 `Task.user_id == project.user_id` 读取条件。保留 `TodoService.get_tasks_by_project` 的用户过滤，并让项目接口显式传入当前用户。
- `FinanceService`：扩展 `_apply_transaction_balance_effect`，区分“反向旧影响”和“应用新影响”；只有应用新的支出/转账扣款时传入余额充足要求。更新前完整校验新流水形态，确认当前流水 flush 后再计算首笔经验。
- `habit_schedule.py`：保留中国周起始、计划日和暂停/请假排除的基础函数。
- 新增一个聚焦的习惯指标辅助模块，负责把完成日期、查询区间、暂停/请假区间和频率转换成统一的计划槽位与完成槽位结果。`TodoService._set_completed_today`、习惯响应、历史响应和统计服务只调用该结果，不各自重新计算。
- `TodoService.backfill_habit`：在插入前调用同一周目标计数器；普通打卡和补记共享“可否再完成”的检查。数据库唯一约束继续作为最后一道同日幂等保护。
- `DailyWorkbenchService`：保留现有用户锁、revision 和请求幂等表；增加对旧 JSON task ID 的防御性解析，非法或已不存在的 ID 只从展示中剔除，不让读取接口 500。更新时继续由用户归属查询决定可保存内容。

### 5.2 前端日期和状态边界

- 扩展现有 `frontend/src/utils/dateTime.js`，提供中国日期键、今天日期、日期键加减和带时区时间显示所需的最小函数集合。
- `Finance.vue`、`FinanceTransactions.vue`、`FinanceDebts.vue`、`Calendar.vue`、`Home.vue` 和习惯历史组件统一调用该工具。
- `useDailyWorkbench` 继续作为工作台异步状态机的唯一入口。页面组件只绑定 `data/loading/error/pending` 等状态，不自行发请求或自行判定成功。
- 工作台完成、快速创建和重点保存分别保持独立的错误/锁状态；刷新只在没有编辑冲突时触发，失败不清空已有内容。
- 前端显示“已完成”“目标已满”“暂停”“请假”等锁定原因，但后端 `409/422/403` 始终是最终权威。

### 5.3 数据和迁移策略

- 本轮优先使用现有表和约束，不新增无法回滚的历史重建任务。
- `habit_completions` 已有的同日唯一约束继续保留；启动回填仍只记录 `last_completed_at` 能证明的日期。
- 不自动修复旧跨用户任务关联；读取隔离测试必须证明非法数据不会泄露，后续可单独生成数据审计报告。
- 不修改既有退款业务规则，不改变已有任务奖励和习惯补记“不领奖”的产品约定。

## 6. 错误和并发处理

| 场景 | API 行为 | 前端行为 |
| --- | --- | --- |
| 项目或任务跨用户 | `403` 或过滤不可见，沿用现有权限语义 | 不展示对方项目名或任务 |
| 修改流水后余额不足 | `400`，事务回滚 | 保留编辑内容，显示可重试错误 |
| 工作台 revision 过期 | `409` | 保留当前草稿，提示刷新后重新选择 |
| 快速创建同 request ID 内容不同 | `409` | 保留输入并生成新的请求上下文 |
| 每周目标已满 | `409` | 不清空历史，提示下周继续 |
| 补记日期不符合计划 | `409/422` | 保留补记表单并显示具体原因 |
| 页面刷新失败 | 请求本身返回错误或状态为失败 | 保留已有成功结果，不显示假失败，不重复提交 |

### 7.3 浏览器验收

使用真实后端和测试账号至少检查桌面宽屏、桌面窄屏、`390px` 移动视口和中国午夜前后：

- 首页：首屏工作台、快速创建、完成任务、今日重点选择/排序/冲突、失败重试。

- 所有失败请求保留已有数据和可重试表单；移动端无横向溢出，焦点和按钮状态可操作。

## 8. 发布门槛

代码实现完成后，必须在根目录 `VERSION` 先递增到下一语义版本，再执行前端版本同步。最终检查至少包括：

```text
cd backend && venv/bin/pytest
cd frontend && npm test
cd frontend && npm run check:version
cd frontend && npm run build
git diff --check
```

Android 包发布时，`versionName` 读取根目录 `VERSION`，`versionCode` 单独递增；需要 debug/release 构建、生产签名、真机安装和安装后核心流程验收。推送 `main` 后必须分别确认 `Test and Deploy` 与 `Build Android Release` 的最终状态为 `success`，并检查 GitHub Release 的 APK、AAB、`latest.json` 和线上健康检查。

## 9. 完成定义

只有同时满足以下条件，才能把相关路线图条目标为完成：

- 六个已复现残留问题都有针对性回归测试并通过。
- FEAT-01 和 FEAT-02 的业务不变量在后端接口、前端状态和浏览器流程中一致。
- 后端全量测试、前端全量测试、版本检查、生产构建和补丁检查通过。
- 浏览器验收覆盖四类视口及中国日期边界。
- Android、CI、线上部署状态按发布门槛取得真实成功证据；仅本地构建或工作流触发不算完成。
